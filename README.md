# BelleGroup train_2M_CN 数据清洗与质量筛选

## 这是什么

这是我跟着教程自学 PySpark 期间做的一个项目。我从 BelleGroup/train_2M_CN 得到这份公开的中文指令数据集用于练手，
目标是把它查看一遍、清一遍，产出一份可以直接用于训练的子集，最后再搭一个看板可视化子集质量。

过程中共涉及三个数据质量假设，全部使用统计脚本实测过，结论请看「假设验证」章节。

## 数据来源

- 数据集：[BelleGroup/train_2M_CN](https://huggingface.co/datasets/BelleGroup/train_2M_CN)
- 规模：2,000,000 条，约 1.8 GB
- 字段：`instruction`（指令）、`output`（回答）
- 下载后放到 `../input/train_2M_CN.json`

## 环境要求

- Python 3.13 / JDK 17 / PySpark
- Windows 环境下需要准备 winutils.exe + hadoop.dll并放在 `E:\hadoop\bin\`
- 写入 MySQL 需要 mysql-connector-java-8.0.13.jar，放在 `../`（或者用环境变量 `MYSQL_JDBC_JAR` 指定）
- 数据库凭据通过环境变量 `MYSQL_USER` / `MYSQL_PWD` 提供

## 运行方式

```bash
# 1. 清洗主流程，产出 ./output/sft_dataset/
python cat.py

# 2. 校验产出，应该打印 1,863,135 条
python output.py

# 3. 生成看板用的宽表并落库（先 dry-run 验证一下）
cd BI看板搭建
python bi_data_prep.py --dry-run
python bi_data_prep.py
```

| 重复 output 组数 | 15,582 组 | — |
| 超长（> 1500 字） | 12,805 | 0.64% |

注意：「重复 output 15,582」是组数，不是条数。这 15,582 组一共涉及 137,656 条记录，
两个数字不能直接相加。

## 清洗策略

按实际执行顺序：

| 步骤 | 规则 | 依据 | 影响条数 |
|:---|:---|:---|---:|
| 1 | 过滤 `output` 长度 < 10 | 太短没有信息量；空输出长度为 0，会被同一条规则一起干掉 | 33,848 |
| 2 | 按 `output` 分组去重，每组保留一条 | 完全重复的回答不增加训练信息 | 103,017 |
| 3 | 派生维度列（`cluster` / `output_len` / `length_bucket` / `has_code` / `has_url` / `has_img`） | 给看板提供可切分的字段 | — |
| 4 | 写出 JSONL，并落库 MySQL | 产出子集，同时留一份可查询的数据源 | — |

处理顺序会影响结果。原始数据里涉及重复的样本一共 137,656 条，如果单独去重应该删 122,074 条；
因为长度过滤先执行，其中 19,057 条重复样本已经跟着过短样本一起删掉了，
所以去重这一步实际影响 103,017 条。

## 假设验证

项目开始时我按直觉提了三个数据质量假设，后来对它们一一进行了统计脚本实测：

| 假设 | 结论 | 证据 |
|:---|:---|:---|
| 长度截断 | 否证 | P95 = 818 和 P99 = 13,535 之间有明显断崖，没有阈值截断的痕迹；超长（≥2000 字）只有 5,151 条，占 0.3% |
| 图片占比高 | 否证 | 含图片标记 3,502 条（0.19%），含链接 7,499 条（0.40%） |
| 模板化严重 | 成立，且比我原来想的更严重 | `instruction` 前 6 字 Top10 句式合计 245,107 条，占 13.2%；单是一个「回答以下问题」就出现了 46,412 次 |

由此得到的结论：

1. 七个类别占比在 5.2% ~ 30.8% 之间，没有哪一类占绝对多数，我原来准备的降采样方案没有可靠的依据，因此我把它放弃了
2. 这份数据的冗余只有 6.8%，因此我们得到：真正的问题在指令句式高度重复。而要不要为模板化做去重或改写，是个决策问题，得看下游任务的需求
3. 含代码块的样本有 246,424 条（13.2%），对 SFT 有价值，清洗时不能误删

## 踩过的坑

1. **写 parquet 时 OOM**
   190 万条长文本挤在 8 个 task 里，Parquet 对字符串列又默认开字典编码，堆内存直接爆炸了。
   报错是一大串 `java.lang.OutOfMemoryError: Java heap space`，看着像是数据有问题，查询一番之后发现其实是内存不够。
   解决方案：提高 driver 堆、把 shuffle 分区数调大、关掉字符串列的字典编码。

2. **有 42 条分类结果对不上**
   Spark 直接统计和落库 MySQL 之后统计的类别分布差了 42 条（0.002%），总数是一致的。
   猜测和 JDBC 写入过程中文本的正则匹配行为有关，没进一步往下查。记到数据字典的已知限制里去了。

3. **Spark 退出时报删不掉 jar**
   `Failed to delete ... mysql-connector-java-8.0.13.jar`，Windows 上 JVM 还锁着文件导致删不掉，
   不影响运行结果。

## 已知限制

- 去重时保留哪一条没有定义。两条 `output` 相同但 `instruction` 不同，留哪条我没有找到依据
- 长度阈值 10 没有验证过，我没抽样确认这 33,848 条是不是真的都没用
- `cluster` 采用关键词匹配，精度有限。七类里「其他」占 30.8%，没做人工校验；
  高频句式「回答以下问题」（46,412 次）没被问答类的关键词命中，落进了「其他」。
  所以「其他」占比偏高有一部分是我规则写得不够，不建议基于这个字段做「砍掉某一类」的决定
- 长度按字符数统计，不是 token 数。要用 token 口径需要另接 tokenizer才行
- 没有做降采样，模板化现象仍然存在，保留了原始分布
- 作为学生练习项目仅在 local[*] 模式下跑过，没上过集群，也没试过更大的数据量
