# 中文指令数据集清洗与质量筛选

对 BelleGroup/train_2M_CN 做数据探查、质量筛选与可视化监控，产出一份可用于 SFT 训练的
中文指令子集，并沉淀指标口径文档。

**核心结论：这份数据的问题不是「脏」，是「单调」。**

---

## 一、数据来源

| 项 | 说明 |
|---|---|
| 数据集 | [BelleGroup/train_2M_CN](https://huggingface.co/datasets/BelleGroup/train_2M_CN) |
| 原始规模 | 2,000,000 条，约 1.8 GB |
| 字段 | `instruction`（指令）、`output`（回答） |
| 存放位置 | `../input/train_2M_CN.json` |

---

## 三、处理策略（按执行顺序）

| 步骤 | 规则 | 依据 | 影响条数 |
|:---|:---|:---|---:|
| 1 | 过滤 `output` 长度 < 10 | 过短无信息量；同时清除空值（空输出长度为 0，自然被覆盖） | 33,848 |
| 2 | 按 `output` 分组去重，每组保留一条 | 完全重复的回答不增加训练信息 | 103,017 |
| 3 | 派生维度列（`cluster` / `output_len` / `length_bucket` / `has_code` / `has_url` / `has_img`） | 供 BI 看板切分与筛选 | — |
| 4 | 写出 JSONL + 落库 MySQL | 产出 SFT 子集，并提供可查询的数据源 | — |

**处理顺序会影响结果。** 原始数据中涉及重复的样本共 137,656 条，单独去重应删 122,074 条；
因长度过滤先行，其中 19,057 条重复样本已随过短样本一并删除，故去重实际影响 103,017 条。

## 四、关键发现（三个假设的实测结果）

项目初期提出三个数据质量假设，**全部用统计脚本实测，而不是凭直觉判断**：

| 假设 | 结论 | 证据 |
|:---|:---|:---|
| 长度截断 | ❌ **否证** | P95 = 818 与 P99 = 13,535 之间存在断崖，无阈值截断痕迹；超长（≥2000 字）仅 5,151 条（0.3%） |
| 图片占比高 | ❌ **否证** | 含图片标记 3,502 条（0.19%），含链接 7,499 条（0.40%） |
| **模板化严重** | ✅ **成立，且高于原判断** | `instruction` 前 6 字 Top10 句式合计 **245,107 条（13.2%）**，单句式「回答以下问题」出现 **46,412 次** |

**由此得出三条结论：**

1. **类别分布不是问题**：七类占比 5.2% ~ 30.8%，不存在单一类别主导 → 原计划的降采样方案失去依据，已放弃
2. **这份数据不是「脏」，是「单调」**：清洗价值不在于去冗余（仅 6.8%），而在于是否要为
   模板化做去重或改写 —— 这是「该不该做」的决策问题，不是「能不能做」的技术问题
3. **含代码样本占 13.2%**（246,424 条），对 SFT 有实际价值，不应在清洗中被误删

## 七、运行方式

```bash
# 1. 清洗主流程（产出 ./output/sft_dataset/）
python cat.py

# 2. 校验产出（应输出 1,863,135 条）
python output.py

# 3. 生成 BI 宽表并落库 MySQL（先 dry-run 验证，不写库）
cd BI看板搭建
python bi_data_prep.py --dry-run     # 只打印统计，不写库
python bi_data_prep.py               # 写入 bigdata.sft_dataset_bi
```

**环境要求**：Python 3.13 / JDK 17 / PySpark / Windows 需 winutils + hadoop.dll；
写库需 mysql-connector-java 驱动，并通过环境变量 `MYSQL_USER` / `MYSQL_PWD` 提供凭据。

### 已知的运行问题

- 写 parquet 时若 shuffle 分区过少（< 8）会 OOM：190 万条长文本集中在少数 task，
  且 Parquet 对字符串列默认启用字典编码，内存占用高。解法是提高 driver 堆、
  增大分区数、关闭字符串列字典编码。
- Spark 退出时清理临时目录会报 `Failed to delete ... mysql-connector-java-8.0.13.jar`，
  属 Windows 文件锁问题，**无害**。

## 八、未解决的问题与已知限制

1. **按 `output` 去重时保留哪一条未定义** —— 两条 `output` 相同但 `instruction` 不同，留哪条没有明确依据
2. **长度阈值 10 未验证** —— 没有抽样确认这 33,848 条是否真的都无价值
3. **分类精度有限** —— `cluster` 用关键词匹配，七类中「其他」占 **30.8%**，未做人工校验；
   高频句式「回答以下问题」（46,412 次）未被问答类关键词命中，说明「其他」占比偏高部分
   来自规则覆盖不足。**因此不建议基于该字段做任何「砍掉某一类」的决策**
4. **长度按字符数统计，不是 token 数** —— 如需 token 口径需另接 tokenizer
5. **统计口径的微小差异** —— Spark 直接统计与 MySQL 落库后统计的类别分布存在 42 条
   （0.002%）差异，总数一致（1,863,135）。推测与 JDBC 写入过程中文本的正则匹配行为有关，
   未进一步定位
6. **未做降采样** —— 数据仍存在模板化现象，保留原始分布
